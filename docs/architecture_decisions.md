# Architecture Decision Log

Status terms: **Accepted** means frozen for the MVP design. **Deferred** means intentionally left for evidence-led implementation work.

| ID | Decision | Reason | Alternatives considered | Why rejected / deferred | Status |
|---|---|---|---|---|---|
| ADR-01 | Use one tool-using agent. | The MVP needs dynamic routing, not separate autonomous departments. | Multi-agent procurement team. | More orchestration, handoffs, and evaluation burden without a business need. | Accepted |
| ADR-02 | Use dual-layer policy architecture: PDF evidence plus structured rules. | Human-readable provenance and deterministic checks solve different problems. | PDF/RAG only; rules only. | RAG-only makes hard decisions non-deterministic; rules-only loses explanation and audit evidence. | Accepted |
| ADR-03 | Compliance status is only `PASS`, `FAIL`, or `REVIEW`. | A compliance result must distinguish confirmed violation from unresolved evidence. | Boolean compliant/non-compliant. | A boolean forces unknown facts into an unsafe conclusion. | Accepted |
| ADR-04 | Separate response outcomes from compliance status. | Clarification and absent historical policy are not business-object compliance outcomes. | One shared status enum. | It conflates user-facing uncertainty with an audit result. | Accepted |
| ADR-05 | Prefer SQL for structured questions first. | Aggregation, filtering, joins, ranking, and basic percentage calculations are auditable in SQL. | Route all data questions through analytics or an LLM. | Adds tool calls and obscures calculations. | Accepted |
| ADR-06 | Call Analytics only when it is materially useful. | Concentration, robust outliers, and reusable decompositions justify deterministic analytics. | Analytics after every SQL query. | Artificial trajectories are poor reliability engineering. | Accepted |
| ADR-07 | PostgreSQL plus pgvector is the current later-stage infrastructure direction. | One platform can host relational procurement data and vector-backed policy chunks. | SQLite plus separate vector store. | Deferred until implementation validates operational simplicity; no database is created yet. | Deferred |
| ADR-08 | Use USD-only transactions. | Eliminates FX ambiguity from ground truth while retaining procurement semantics. | Multi-currency with exchange rates. | Adds irrelevant accounting and historical-rate complexity. | Accepted |
| ADR-09 | Fix `EVAL_AS_OF_DATE` to 2026-06-30. | Relative-date prompts need repeatable answers. | Evaluate relative to runtime date. | Golden cases would drift over time. | Accepted |
| ADR-10 | Use `ISSUED`, `CLOSED`, `CANCELLED` as the only PO states. | This is enough to set spend and audit boundaries. | Full requisition-to-pay lifecycle. | It models ERP workflow rather than evidence needs. | Accepted |
| ADR-11 | Determine contract validity at PO time. | A linked ID alone cannot establish applicable coverage. | `contract_id IS NOT NULL`. | Ignores unresolved references, dates, status, supplier, and category mismatch. | Accepted |
| ADR-12 | Enforce approval requirements deterministically. | The core rule is >$50k, two valid purchase approvals, including one Director. | LLM-only policy interpretation; role hierarchy. | LLM outcomes are not repeatable; hierarchy is outside MVP evidence needs. | Accepted |
| ADR-13 | Treat supplier concentration as risk, not automatic violation. | High concentration requires context and mitigation interpretation. | Convert 80% share directly to FAIL. | It would incorrectly turn analytics into a hard policy engine. | Accepted |
| ADR-14 | Exclude invoices, receipts, payments, and three-way matching. | No retained MVP scenario requires them. | Procure-to-pay expansion. | Scope creep would dilute SQL/RAG/compliance reliability work. | Accepted |
| ADR-15 | Do not introduce multi-agent architecture prematurely. | A single agent with four bounded tools is the smallest complete system. | Specialist SQL/RAG/compliance agents. | Agent-per-function adds complexity without independent autonomy needs. | Accepted |
| ADR-16 | Require `PolicyRule → canonical PolicyChunk` provenance. | The rule engine must cite its exact human-readable source without re-running retrieval. | Detached YAML/JSON rules. | Detached rules become an un-auditable second source of truth. | Accepted |
| ADR-17 | Contract requirements apply only to IT Services and Professional Services categories. | This directly matches retained compliance scenarios while keeping applicability explicit and small. | Global contract requirement; separate policy-applicability framework. | A global rule creates false FAILs; a framework is unnecessary for two category flags. | Accepted |
| ADR-18 | Use MAD robust z-score for comparable item-price outliers. | It is deterministic and robust to planted price anomalies. | Mean/std-dev z-score; unit conversion. | Mean/std-dev is distortion-prone; conversion is outside scope. Only same item, UOM, USD groups with at least eight rows are comparable. | Accepted |
| ADR-19 | Use SQLite via SQLAlchemy for Phase 2B local loading and tests. | It is deterministic, zero-setup, relational, and fast for the generated dataset. | PostgreSQL now; CSV-only access. | PostgreSQL infrastructure is premature; CSV-only access cannot exercise relational joins, metadata, or read-only query safety. PostgreSQL + pgvector remains the later target. | Accepted — temporary backend |
| ADR-20 | Generate the policy corpus from editable Markdown with a checked manifest. | It keeps policy wording reviewable while preserving deterministic document IDs, versions, sections, and page locations for citations. | Hand-authored PDFs; retrieval-only source files. | Hand editing makes page-level provenance drift; retrieval files alone do not provide a human-readable artifact. | Accepted |
| ADR-21 | Keep structured policy rules as a small provenance-bearing manifest. | The 2026 approval and contract rules need deterministic inputs without introducing a general policy language. | Encode rules only in PDFs; introduce a DSL now. | PDFs alone are unsuitable for deterministic checks; a DSL is premature for two MVP hard rules. | Accepted |
| ADR-22 | Ingest generated PDFs rather than Markdown for retrieval. | The portfolio system must prove PDF extraction and preserve the artifact users will cite. | Retrieve authoring Markdown directly. | It bypasses the actual policy-document ingestion path. | Accepted |
| ADR-23 | Use page-bounded, section-aware canonical chunks with deterministic IDs. | A future citation requires one unambiguous page and section, while stable IDs support rules and regression evals. | Fixed token windows; cross-page chunks; UUIDs. | They weaken provenance or reproducibility. | Accepted |
| ADR-24 | Apply temporal validity filtering before all ranking. | Historical queries must never be ranked against inapplicable policy versions. | Rank globally then discard later. | It can leak a newer policy into evidence selection. | Accepted |
| ADR-25 | Compare BM25, CPU exact dense search, and RRF on the same local corpus. | Retrieval quality must be measured before choosing vector-storage infrastructure. | One unmeasured retriever; ANN now. | A 30-chunk corpus does not justify ANN or hide ranking differences. | Accepted |
| ADR-26 | Use deterministic retrieval metrics and recorded failure traces only. | Curated evidence targets make Hit@k, Recall@k, and MRR auditable. | LLM-as-judge for retrieval. | It adds non-determinism without improving this benchmark. | Accepted |
| ADR-27 | Integrate the canonical policy chunk registry with a dedicated PostgreSQL + pgvector table, while keeping SQLite procurement data unchanged. | The deployment-target retrieval store can be verified against the Phase 2D local oracle without broadening the structured-data migration scope. | Keep only local NumPy search; migrate all structured tables now. | Local-only search does not exercise the target vector database; a structured-data migration is unrelated to retrieval correctness. | Accepted |
| ADR-28 | Use exact pgvector cosine search with temporal SQL filtering before ranking and no ANN index. | Thirty chunks need correctness and rank equivalence, not approximate-search performance. | HNSW; IVFFlat; filter after ranking. | ANN adds unnecessary tuning and can obscure differences; late filtering can expose invalid policy versions. | Accepted |
| ADR-29 | Evaluate the two current hard rules through explicit deterministic Python evaluators over SQLite PO facts. | Approval and contract semantics are small, stable, auditable, and do not require semantic policy interpretation. | LLM reviewer; generic rules engine; retrieve policy text during evaluation. | These would make hard decisions less deterministic or add abstraction beyond two rule families. | Accepted |
| ADR-30 | Treat absent executable rule coverage as `REVIEW`, and keep non-applicability separate from rule PASS. | A 2025 PO cannot be judged by 2026-only structured rules, while a threshold or category that does not trigger a rule is not evidence of passing that rule. | Apply 2026 rules historically; emit PASS for skipped rules. | Both alternatives overstate deterministic policy coverage. | Accepted |
| ADR-31 | Keep analytics to explicit spend drivers, MAD price comparison, and concentration risk; leave ordinary aggregation and Pareto SQL-first. | These three calculations are reusable deterministic analysis beyond a normal SQL result, without becoming arbitrary code execution. | Analytics after every query; generic Python tool; ML anomaly platform. | They would add uncontrolled behavior or duplicate existing SQL capabilities. | Accepted |
| ADR-32 | Define task-level golden evaluation before Agent implementation. | Tool selection, evidence requirements, and abstention behavior need a stable contract before prompts or orchestration can bias the benchmark. | Build the Agent first and derive cases later. | It would make regression evaluation conform to implementation accidents. | Accepted |
| ADR-33 | Model required, optional, and unnecessary tools separately. | A valid route may contain optional work, while gratuitous calls must remain measurable. | One expected-tool set; only exact trajectories. | It cannot distinguish flexible correctness from wasteful behavior. | Accepted |
| ADR-34 | Represent acceptable routes plus explicit ordering constraints. | Independent retrieval and compliance explanation can occur in more than one safe order, while Analytics and fact-based compliance have dependencies. | One rigid trace for every task; no ordering checks. | Rigid matching rejects valid behavior; no ordering permits impossible workflows. | Accepted |
| ADR-35 | Keep compliance status separate from response outcome in task evaluation. | A REVIEW audit can be clearly answered, while missing historical policy is an insufficient-evidence response. | One shared evaluator status. | It repeats the earlier semantic conflation at the task layer. | Accepted |
| ADR-36 | Use deterministic pre-Agent trajectory and citation checks; do not publish a composite Agent score or use an LLM judge. | The corpus has curated facts and PDF-derived evidence targets that support repeatable checks. | LLM-as-judge; weighted Agent score. | Neither is needed before generated answers exist, and a weighted score hides failures. | Accepted |
| ADR-37 | Expose the four capabilities through framework-neutral typed adapters before Agent orchestration. | Stable business APIs and error contracts should precede a framework-specific Agent binding. | Add LangGraph tools directly; expose components unwrapped. | Direct framework binding mixes orchestration with business contracts; raw components lack uniform metadata/errors. | Accepted |
| ADR-38 | Let Analytics and Compliance internally load their bounded structured facts. | Domain parameters avoid LLM-mediated row transfer while preserving component ownership and auditability. | Require SQL before every domain call; pass arbitrary fact payloads. | Both create redundant calls or malformed, duplicated business facts. | Accepted |
| ADR-39 | Keep general SQL for ad-hoc facts while treating redundant SQL calls before domain tools as unnecessary. | SQL still serves direct facts, joins, ranking, and aggregation; domain results already include their relevant facts. | Remove SQL; retain SQL as required for all tasks. | Removing it loses flexible structured access; forced SQL lowers tool-selection precision. | Accepted |
| ADR-40 | Return typed structured tool outputs and normalized errors with execution metadata. | Future trace evaluation and framework adapters need consistent JSON-safe contracts without prose generation. | Prose-only outputs; raw exceptions. | Prose cannot be reliably evaluated; raw exceptions expose implementation details. | Accepted |
| ADR-41 | Default the policy tool to local hybrid retrieval and report its actual backend. | Hybrid has the best accepted offline score, while pgvector currently validates dense-only equivalence. | Pretend hybrid is pgvector; default to unmeasured backend behavior. | It would misrepresent infrastructure and hide retrieval composition. | Accepted |
| ADR-42 | Use one explicit LangGraph model/tool loop over the Phase 3A registry. | It makes dynamic, multi-step bounded execution observable without copying business logic into orchestration. | OpenAI Agents SDK; multi-agent hierarchy; fixed pipeline. | A second orchestration SDK or specialist-agent handoffs add scope; a fixed pipeline cannot demonstrate routing. | Accepted |
| ADR-43 | Keep the OpenAI integration as a thin environment-configured adapter and use scripted model turns for ordinary tests. | Live calls should be replaceable and must not make deterministic regression spend credits. | Hard-code a provider in graph nodes; mock tools only. | The former couples control flow to a provider; the latter cannot test real tool-loop state transitions. | Accepted |
| ADR-44 | Validate final citations and tool-call references against run-local observed evidence. | Grounding requires deterministic rejection of invented policy metadata, even after structured model output validation. | Trust model JSON; validate only after offline eval. | Well-formed JSON can still cite nonexistent evidence. | Accepted |
| ADR-45 | Enforce model-turn, total-tool-call, and identical-call limits in the graph. | Bounded autonomy is a reliability requirement, not prompt advice. | Prompt-only limits; unbounded retries. | They cannot safely terminate looping calls. | Accepted |
| ADR-46 | Exclude chain-of-thought and persistence from MVP Agent traces. | Observable tool actions, final output, and usage are sufficient for evaluation without retaining hidden reasoning or introducing storage infrastructure. | Save reasoning/persistent thread memory. | Both create unnecessary safety, privacy, and implementation scope. | Accepted |
| ADR-47 | Version Agent routing instructions and evaluate `agent_v2` against a preserved `agent_v1` live baseline. | Prompt-only routing changes need a reproducible A/B record without mutating data, tools, or the baseline. | Tune components in place; overwrite the baseline; add a keyword router. | Component changes would confound the comparison, an overwritten baseline removes evidence, and a keyword router would duplicate brittle orchestration logic. | Accepted |
